# 送审执行清单：提审到过审

适用分支：`main`

适用目标：当前 iOS 送审 / TestFlight / App Store 审核窗口

---

## 一、提审前要做什么

### 1. 确认当前主线状态

- `SparkRing` 通道可见且可用
- `好友模式` 不再暴露
- `Max tier` 前端入口已禁用
- 不暴露 `wallet / top-up / Spark 币支付`
- `npm run type-check` 通过
- `npm run build` 通过

### 2. 通知后端做临时审核策略

如果不想先查 `install_id`，可以直接让后端在审核窗口内临时调高 `experience` 配置。

建议：

- `experience` 总额度临时提高到 `100`
- `experience` 日额度同步提高到足够审核使用
- 保持现有防刷策略开启
- 审核结束后恢复默认值

如果不走“全量提高”方案，就走“指定 install_id 提额度”方案：

- 真机先启动一次 app
- 读取 `mms-install-id`
- 发给后端
- 让后端只给该 install_id 对应 token 提额度

### 3. 让后端确认这 4 件事已经上线

- `max tier` 默认关闭
- `MAX_TIER_WHITELIST` 只给内部需要的 install_id
- `daily_quota_exceeded / insufficient_user_quota / rate_limited` 已统一
- `provision` 防刷已生效

### 4. 真机 smoke 前注意

- 不要卸载 app
- 不要清 app 数据
- 不要反复换测试容器

原因：

- 当前 key 绑定的是“安装实例”
- 不是“这台 iPhone 永久固定一个 key”
- 卸载重装、清数据、换 origin / container，都可能生成新的 `install_id`

---

## 二、提审前真机 smoke 要做什么

### 1. 冷启动

- 打开 app
- 确认不白屏、不闪退

### 2. Setup

- 打开 `SetupGuide`
- 点击“先试试看”
- 确认能进入体验路径
- 确认不要求先手动填 API Key

### 3. Chat

- 进入 `Chat`
- 打开模型选择器
- 确认至少有一个可用模型
- 发送一条短消息
- 确认成功返回

建议测试文案：

`你好，给我一句 20 字以内回复`

### 4. Discuss

- 进入 `Discuss`
- 启动一次讨论
- 确认主按钮不死
- 确认结果能渲染

### 5. Creative Lab

依次进入这些可见页面：

- `challenge`
- `story-lite`
- `story-live`
- `multi-life`
- `turtle-soup`

每个页面至少确认：

- 能进去
- 不白屏
- 不报明显运行时错误
- 能完成一次最小交互

### 6. Settings

- 打开 `Settings`
- 确认主题切换正常
- 确认 provider 列表正常
- 确认 `SparkRing` 可见
- 确认没有 `Max tier` 可触发入口
- 确认没有 `好友模式`、支付、充值相关残留

### 7. 错误提示

至少确认前端文案语义正确：

- `daily_quota_exceeded`
  - `今日额度已用完，明天 UTC 0 点重置`
- `insufficient_user_quota`
  - `账户额度已耗尽，请联系支持申请更多额度`

---

## 三、提审时要做什么

### 1. 提审前最后确认

- 当前包来自 `main`
- 后端审核期额度策略已经生效
- 真机 smoke 已通过

### 2. 提审后先不要做的事

- 不要立刻改回审核期额度
- 不要重开 `Max tier`
- 不要把 wallet / top-up 合回 `main`

### 3. 提审期间保持什么状态

- 保持 `experience` 审核期额度策略有效
- 保持 `max tier` 关闭
- 保持 `provision` 防刷开启
- 不删除用于审核复现的后端记录

---

## 四、提审期间要观察什么

### 1. 看这几类异常

- 审核 / 演示用户是否撞到额度不足
- 是否出现异常多的新 provision key
- 是否有明显刷子在打 `provision`
- 是否有频繁 `rate_limited`

### 2. 如果后台看到 key 变多，不要先慌

当前一台 iPhone 不是“永远一个 key”，而是“单次安装实例一个 key”。

下面这些情况都会新建 install_id / 新 key：

- 卸载重装
- 清 app 数据
- 网页端清 Local Storage
- 浏览器切 profile / 无痕
- 不同 origin / 不同容器

所以“后台 key 变多”不一定是漏洞，也可能是测试环境反复创建。

---

## 五、过审后要做什么

### 1. 立即恢复后端额度策略

如果你走的是“审核窗口内全量提高 experience 额度”方案，过审后要立即改回：

- `experience` 总额度改回默认值
- `experience` 日额度改回默认值

### 2. 保持这些不动

- `max tier` 默认关闭
- `MAX_TIER_WHITELIST` 只给内部
- `provision` 防刷继续保留
- 错误码统一不要回退

### 3. 过审后下一步再做

- 再决定是否恢复更精细的 install_id 白名单策略
- 再决定是否接自建埋点
- 再决定是否推进 wallet / top-up 分支

---

## 六、最简执行版

如果你现在只想看最短步骤，就按这个走：

1. 让后端在审核窗口内把 `experience` 临时提到 `100`
2. 确认后端已关闭 `max tier`
3. 真机跑一遍首装、Chat、Discuss、Creative Lab、Settings
4. 提审
5. 提审期间不要改回额度
6. 过审后把 `experience` 改回默认值

---

## 七、当前关键事实

- 当前前端已经兼容后端真实返回的 `insufficient_user_quota`
- 当前前端送审版不再开放 `Max tier`
- 当前 `install_id` 是安装实例级，不是物理设备永久唯一
